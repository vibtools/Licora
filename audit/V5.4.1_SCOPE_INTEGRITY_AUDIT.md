## Confirmed defects corrected in v5.4.1

### P0 — updater browser controller DOM mismatch

`admin/assets/js/licora-updater.js` referenced `#update-log-title`, while `admin/updates.php` rendered `#licora-update-log-title`. A real update job could therefore be persisted at `running / fetch_manifest / 1%`, after which `renderJob()` threw a null-property TypeError before `openModal()` and `driveJob()` executed. The same mismatch existed in v5.3.0 and was exposed by the first real v5.3.0 → v5.4.0 upgrade.

Correction: exact selector alignment, startup DOM validation, dedicated DOM contract test and Node browser-runtime fixture.

### P1 — terminal jobs treated as active frontend state

The browser used truthiness of `state.job` rather than updater status. Retained terminal jobs could therefore block a later preflight/install in the same page session.

Correction: only `running` and `rollback_running` are active frontend states.

### P2 — native browser confirmation bypassed the v5.4 UI contract

Install and rollback used browser-native `confirm()`, producing a platform/browser dialog outside the reusable Licora Light component system.

Correction: reusable light confirmation modal for install/rollback.

### P1 — PHP-stream package fallback buffered full ZIP in memory

cURL streamed release packages to disk, but the documented PHP-stream fallback read the complete package into memory before saving it. This could fail on shared/cPanel hosts even though stream transport passed preflight.

Correction: bounded chunked stream-to-disk download with redirect validation, byte limit and write/flush verification.

### P1 — archive-entry validation gap

Directory entries were skipped before path/type validation. Runtime validation also lacked explicit unsupported-special-entry and case-collision rejection.

Correction: validate every non-root path before directory handling; reject symlinks, unsupported special entries, traversal and case-colliding source paths before extraction.

### P1 — backup/write integrity gaps

Database safety-dump writes and source-backup manifest writes were not consistently checked for short/failed writes. Source rollback backups did not persist a content-hash inventory.

Correction: exact-write checking, SHA-256 source-backup inventory, copy verification, database-backup final verification and rollback restore hash verification. Legacy in-flight jobs created by v5.3.0/v5.4.0 remain rollback-compatible when their older backup context lacks the new hash map.

### P1 — release builder/runtime validation parity gaps

The runtime rejected protected/deletion overlap cases that the builder did not reject before signing. Migration duplicate/idempotency validation was also not fully mirrored.

Correction: builder/runtime parity for protected paths, delete/package overlap, case collisions, duplicate migration IDs and non-destructive idempotency requirement.

### P1 — release artifact was not re-run through installed runtime verifier

The tag workflow verified the cryptographic signature but did not extract the exact signed artifact through Licora's own `ManifestVerifier` + `ArchiveValidator` before publication.

Correction: `scripts/verify-release-update.php` runs after signing and before GitHub Release creation.

## Fake/demo/placeholder audit

No fake updater state engine, fake update progress source, fake deployment log stream or production `AI Diagnostics` implementation was found. `update_jobs` and `update_events` are real database persistence paths. The installer has an explicit optional demo-data feature; it predates the updater/UI scopes and is legitimate, not hidden updater fakery.

## v5.4 UI scope audit

- Primary navigation is implemented through the shared sidebar registry.
- `admin/includes/navbar.php` is a compatibility entrypoint that renders shared sidebar/topbar components.
- Licora Light remains the production theme target.
- Tailwind runtime/page `<style>` migration rules remain enforced.
- No database/API/license/device/cron behavior change is required by this hotfix.

## Explicit documented limitations retained, not misreported as fixes

- Database safety dump is not an automatic full SQL restore engine.
- Automatic updater history/backup retention GC is not implemented.
- Signing-key rotation has no dual-key transition protocol yet.
- Beta/dev update channels are not implemented.

These are documented operational limits and remain outside the v5.4.1 corrective scope.

## Production incident recovery boundary

A persistent pre-critical v5.3.0 → v5.4.0 job at `fetch_manifest / 1%` must not be manually deleted or rewritten. A separate minimal browser-controller rescue overlay is provided so the existing job can resume with its original backend/job identity. The main v5.4.1 release remains a clean v5.4.0 → v5.4.1 source delta and also signs direct compatibility with reviewed 5.3.0/5.4.0 updater baselines for installations without a conflicting active job.
