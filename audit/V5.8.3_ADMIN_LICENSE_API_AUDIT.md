# Licora v5.8.3 Admin License Control API Audit

## Scope lock

The approved delta is limited to dedicated Admin API key control, order-driven license/device lifecycle endpoints, additive persistence, Admin Settings integration, tests/docs and v5.8.3 release identity. Existing API v1/v2 client behavior is frozen. Application creation via the new API is forbidden.

## Control findings

| Boundary | Implemented control |
|---|---|
| Credential separation | Dedicated `licora_admin_live_…` / `licora_admin_test_…` bearer tokens; only SHA-256 hashes and display prefixes are stored. |
| Transport | HTTPS required by default; trusted forwarded protocol honored only through the existing explicit proxy setting. |
| Request integrity | HMAC-SHA256 covers exact method, request target including query, timestamp, nonce and exact body hash. |
| Replay | Bounded clock skew plus persistent unique per-key nonce. |
| Duplicate orders | Required idempotency key, unique `(api_key_id, external_order_id)`, normalized request hash and conflict detection. |
| Authorization | Granular scopes plus exact assigned active-app check on every license/device operation. |
| Object isolation | Every managed license must have an `admin_api_license_orders` mapping owned by the calling key. |
| Secret exposure | Full API secret is shown once after create/rotate; full license key requires `license:reveal`. Logs store no credential/body. |
| Destructive behavior | Key revoke is permanent; license delete is a tombstone/soft delete. Ban/delete revoke device credentials and refresh tokens. |
| Abuse controls | Optional IPv4/IPv6 CIDR allowlist, per-key hourly rate limit, expiry, suspension/revocation and audit request IDs. |
| App scope lock | The API queries existing active `v2_client_apps`; source contains no `INSERT INTO v2_client_apps`. |

## Data change

`migration-v5.8.3-admin-license-api.sql` adds seven InnoDB tables. It contains no `ALTER`, `DROP`, `TRUNCATE` or `RENAME` statement and changes no existing record. The same schema is appended to `database.sql` for fresh installs. The signed release specification declares it once as non-destructive and idempotent from v5.8.2.

## Verification gates

- Frozen API v1 blob hashes remain enforced by `scripts/verify-local.py`.
- PHP syntax is checked recursively on PHP 8.0–8.4 in CI.
- `tests/admin_api_static.php` validates routes, security markers, exact canonicalization, HMAC failure, IPv4/IPv6 CIDR behavior, additive SQL and absence of app creation/hard license deletion.
- `tests/admin_api_db_integration.php` validates migration idempotence, order idempotency/conflicts, exact app binding, legacy v1 key non-binding, key ownership isolation, status/list/actions, device/token revoke, ban/blacklist and soft delete against MySQL 8.4.
- Existing API v2, updater, Dashboard, UI, installer, security and compatibility suites continue to run.

## Residual operational requirements

- Production must use HTTPS and a server-side secret store.
- IP allowlists should be configured when the order server has stable egress addresses.
- Order systems must reuse the same order data and idempotency key when retrying uncertain network results.
- A main-branch CI pass is required before v5.8.3 may be tagged or published.
