## 3. Implemented Secure API v2

New public-client endpoints:

- `POST /api/v2/activate.php`
- `POST /api/v2/refresh.php`
- `POST /api/v2/status.php`
- `POST /api/v2/deactivate.php`

Security model:

- no v1/shared Licora API key is required or accepted as a v2 client credential;
- RSA-3072/SHA-256 server-signed short-lived access tokens with fixed `RS256` and `LICORA-V2` token type;
- ECDSA P-256/SHA-256 device proof for signed requests;
- app/license/device binding;
- timestamp and one-time nonce replay defense;
- SHA-256-only refresh-token storage, rotation, family reuse revocation, and device revocation;
- pre-auth global IP rate limiting before expensive proof/token processing;
- app/device-specific rate limits after identity resolution;
- generic external errors and separate v2 audit records;
- status/deactivate/refresh verify the device proof before persisting the nonce, preventing unauthenticated nonce poisoning;
- refresh requires `app_version` and rechecks the Client App minimum-version policy.

## 4. Additive database scope

`migration-v5.2.0-api-v2.sql` creates only:

1. `v2_client_apps`
2. `v2_device_credentials`
3. `v2_refresh_tokens`
4. `v2_used_nonces`
5. `v2_audit_logs`

The migration contains no `DROP`, `TRUNCATE`, or `RENAME`. Fresh `database.sql` appends the same additive v2 migration. Existing v1 tables and license format remain intact.

For first activation, API v2 locks the license row within a transaction before enforcing device limits and registering/binding the device, avoiding a concurrent first-activation oversubscription path in the new v2 flow without changing v1 behavior.

## 5. Signing-key lifecycle

Fresh v5.2.0 installer runs generate a deployment RSA-3072 signing pair atomically. The private key is never displayed. Existing deployments use `php scripts/setup-v2.php`, which applies only the additive migration and generates a key pair only when neither key exists; a partial pair is rejected.

Default deployment paths:

- `includes/.licora-v2-signing-private.pem`
- `includes/.licora-v2-signing-public.pem`

Both paths and temporary installation variants are gitignored. `includes/.htaccess` continues to deny direct Apache web access. Production deployments may configure key paths outside the web root. No generated PEM key is included in source or release artifacts.

## 6. Admin/UI integration

Added real-data admin pages:

- `admin/client_apps.php`: manage public Client App IDs, enable state, minimum version, token TTL, clock skew, and rate policy.
- `admin/v2_devices.php`: inspect v2 device credentials using truncated identifiers/fingerprints and revoke a device.

Existing License Management retains the API-v1 API-key selector. A separate API-v2 Client App selector sets an exact active `app_scope` only when no v1 API key is selected; submitted v2 app IDs are server-validated against active Client Apps.

No fake/demo runtime values or unsupported controls were added to these pages.

## 7. CI and release automation

Normal pushes/PRs run the repository verifier across PHP 8.0-8.4, then a dedicated MySQL 8.4 API-v2 integration job. The release-candidate package artifact is produced only after validation and DB integration dependencies succeed.

Tag `v5.2.0` triggers `.github/workflows/release.yml`, which verifies tag/version alignment, runs full source/security/DB checks, builds the exact tagged source ZIP via `scripts/package-release.sh`, writes SHA-256, and creates the GitHub Release from `RELEASE_NOTES_v5.2.0.md` with ZIP/checksum assets. GitHub's normal tag source archives remain separate from the custom verified release ZIP.

Local release publication commands are no longer required. `scripts/verify-local.py` validates source only and never creates tags/releases.

## 10. Known operational requirements, not implementation defects

- Production API v2 requires HTTPS unless explicitly configured otherwise for controlled development.
- Existing deployments must run `php scripts/setup-v2.php` after source upgrade to create v2 tables and deployment signing keys.
- Server operators must preserve/back up the v2 private signing key; losing it requires intentional signing-key rotation and invalidates outstanding access tokens.
- Nginx/LiteSpeed deployments must reproduce the existing private-`includes/` web-deny policy because `.htaccess` is Apache-specific.
- API v1 retains its historical security/compatibility characteristics by explicit scope lock.
