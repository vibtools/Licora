## 3. Current Actual Dashboard Architecture

### Render path

`admin/index.php` server-side PHP দিয়ে Dashboard render করে। Authentication-এর পরে:

1. `LicenseSystem::getStats()` runs license/device count queries.
2. `api_keys` aggregate query runs.
3. `api_logs` থেকে 14-day activity query runs.
4. license expiration ±30-day query runs.
5. `api_logs` থেকে top licenses query runs.
6. `api_logs` থেকে last 10 calls query runs.
7. PHP সম্পূর্ণ HTML render করে.
8. Chart.js server-rendered arrays দিয়ে charts তৈরি করে.
9. JavaScript 30 seconds পরে `window.location.reload()` করে.

**Verdict:** Current Dashboard is **server-rendered snapshot + periodic full-page reload**, not a live partial-refresh dashboard.

## 5. Data Truthfulness Findings

### 5.1 `System Status = Live`

`Live` is derived from:

`ENVIRONMENT === 'production' ? 'Live' : 'Dev'`

It is **environment identity**, not a health probe.

**Classification:** `[MISLEADING LABEL]`

Required production correction: label it truthfully as `Environment / Production` or derive health from measured checks.

### 5.2 Hardcoded system status rows

Dashboard displays:

- Database — `Connected`
- Security — `Active`
- API Server — `Running`
- Environment — configured environment

`Security = Active` and `API Server = Running` are static presentation strings.

**Classification:** `[NOT LIVE TELEMETRY]`

### 5.3 Database status

The dashboard performs database queries before rendering, so a rendered page implies DB access succeeded. However the status row itself does not perform an explicit health probe.

**Classification:** `[PARTIALLY REAL]`

### 5.4 Daily API Requests

Dashboard reads `api_logs`.

Forensic write search shows `api_logs` is written by `api/verify.php`.  
`api/check_license.php` does not insert into `api_logs`.  
Secure API v2 uses `v2_audit_logs`.

Therefore `Daily API Requests` is not all Licora API traffic.

**Classification:** `[INCOMPLETE METRIC SCOPE]`

### 5.5 Top Used Licenses / Recent API Calls

These also read `api_logs`; therefore they represent the same tracked legacy/API-v1 verification stream, not API v2 and not the unauthenticated compatibility endpoint.

**Classification:** `[INCOMPLETE METRIC SCOPE]`

### 5.6 Expired Trend

Current query includes:

- 30 days in the past
- 30 days in the future

but the title is `Expired Trend`.

**Classification:** `[MISLABELED]`

Required correction: separate past-expired vs upcoming-expiration semantics or rename to `Expiration Timeline`.

### 5.7 Active Devices

Current metric:

`COUNT(*) FROM devices WHERE is_active = TRUE`

Device freshness depends partly on `last_active` and external `cron/cleanup.php`. API v2 also tracks fresher presence in `v2_device_credentials.last_seen_at`.

**Classification:** `[PARTIAL PRESENCE MODEL]`

The dashboard must not claim real-time presence unless the read model explicitly defines recency.

### 5.8 Recent API Calls pagination

The query loads only 10 rows and UI page size is also 10.

**Classification:** `[REDUNDANT PAGINATION]`

## 6. Reload / Live Update Findings

### Dashboard

Current code:

```javascript
setTimeout(() => {
    window.location.reload();
}, 30000);
```

**[CONFIRMED]** Full-page reload every 30 seconds.

Not implemented:

- generic dashboard AJAX endpoint
- dashboard polling controller
- SSE
- WebSocket
- incremental KPI refresh
- incremental chart refresh
- incremental recent-activity refresh

### Other admin pages

Most admin pages are server-rendered snapshots. Existing shared JavaScript search/pagination manipulates already-loaded DOM; it does not fetch new DB rows.

### Existing asynchronous exception

The Update Center already has a real AJAX/resumable workflow using `admin/ajax/update-*.php` and `admin/assets/js/licora-updater.js`. This architecture is useful as an internal coding/style reference, but updater state-machine behavior must not be reused or altered for dashboard refresh.

## 7. Background Database Mutation Findings

Database data can change without an admin page being open:

- `api/verify.php`
- `api/check_license.php`
- Secure API v2 endpoints
- Admin CRUD actions
- `cron/cleanup.php`
- DB triggers

`cron/cleanup.php`:

- marks expired licenses expired
- marks stale devices inactive
- deletes old inactive devices
- deletes old logs
- removes old rate-limit rows
- removes old failed-login rows

The cron process requires an external OS/cPanel scheduler. Licora does not run its own daemon.

`cron/check_expiring.php` currently prints expiring-license information. The source comments mention email notification as a possible future action, but no email notification engine is implemented.

## 8. Current Error-Handling Baseline Relevant to This Update

[CONFIRMED]

- Production config disables error display and enables error logging.
- Database connection logs detailed PDO failure; production response is generic.
- API v2 uses typed `V2Exception` with machine code + HTTP status and generic internal 500 handling.
- Update Center uses typed `UpdateException`, structured JSON errors and generic internal failures.
- Installer maps internal errors to sanitized public messages and logs internal failures.
- CSRF failures are rejected.
- Admin authentication is checked before protected pages.
- Current actual auth code enforces 30-minute inactivity timeout inside `Auth::isAdminLoggedIn()`.

### Documentation conflict resolved

Older `docs/FEATURE_MATRIX.md` states session inactivity timeout is “Defined, not enforced.” Actual v5.5.1 source now enforces it in `isAdminLoggedIn()`.

**Authority rule for this update:** actual frozen source > stale documentation.
