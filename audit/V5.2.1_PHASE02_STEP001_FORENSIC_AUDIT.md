## 2. Findings and root causes

### 2.1 GitHub Dependabot CI false failures

The v5.2.0 `main` CI itself completed successfully, including the PHP validation matrix, API v2 MySQL integration and verified source artifact job. Dependabot branches upgrading `actions/checkout` and `actions/setup-node` from v6 to v7 failed before PHP tests because `scripts/verify-local.py` required literal `actions/...@v6` strings.

Root cause: the verifier treated an exact workflow-action major as a source contract rather than validating a supported minimum version. A valid dependency upgrade therefore looked like a missing CI marker.

Fix:

- CI/release workflows use `actions/checkout@v7` and `actions/setup-node@v7`.
- verifier action checks parse numeric action tags and enforce supported minimum versions rather than exact v6 strings.
- PHP 8.0-8.4, MySQL 8.4 integration, exact-ref packaging, source artifact and automatic release gates remain in place.

### 2.2 Existing/cPanel API v2 provisioning depended on CLI

v5.2.0 fresh installations provision API v2 through the installer, while an existing installation needed `php scripts/setup-v2.php`. This is valid on shell-capable hosts but incomplete for cPanel/shared hosts without Terminal.

The user-provided local `setup-v2.php` run failed with a database connection-refused error while the source verifier passed. That specific failure is an environment/database-service connectivity condition, not a PHP syntax failure. v5.2.1 does not alter the frozen database connection class.

Fix:

- Added shared `V2Provisioner` for the existing additive migration and signing-key readiness.
- CLI `scripts/setup-v2.php` reuses the provisioner.
- Existing **Admin -> Client Apps** adds an authenticated, CSRF-protected **Initialize API v2** action for cPanel/shared-hosting deployments without shell access.
- No new admin page, database table or migration is introduced by v5.2.1.

### 2.3 Refresh app/device rate-limit rollback gap

In v5.2.0 refresh flow, refresh-token row locking opened a PDO transaction before app/device rate-limit writes. A later invalid device proof could roll back that same transaction, undoing those app/device counters. The independent pre-auth IP bucket remained active, but the planned app/device refresh buckets were not guaranteed to persist on failed proofs.

Fix:

- `V2Repository::refreshRateLimitContext()` resolves only the app/device rate-limit identity without opening the refresh row-lock transaction.
- refresh app/device buckets are consumed before `refreshContextForUpdate()` begins the token transaction.
- the token rotation/reuse transaction semantics remain unchanged.

### 2.4 Server signing private/public pair was not cross-validated

v5.2.0 validated that both PEM files were individually parseable, but did not explicitly prove that the public file corresponded to the configured private key.

Fix:

- `V2KeyManager::assertPairMatches()` derives the public key from the private key and compares it to the configured public key.
- runtime API v2 bootstrap fails closed on a mismatched pair.
- CLI/admin provisioning validates existing pairs and never silently replaces a partial or mismatched pair.
- crypto regression tests include a deliberate mismatched-key pair.

### 2.5 Release documentation still contained a manual publication path

The v5.2.0 code already made tag-triggered GitHub Actions the authoritative publisher, but the release guide retained a historical manual `gh release create` sequence. That conflicted with the approved automatic-release workflow.

Fix: v5.2.1 release documentation makes the tag-triggered workflow authoritative; the package script remains only for forensic/manual package inspection.

## 7. Installer and cPanel overwrite verification

Fresh install behavior remains the v5.2.0 design with release-version synchronization to v5.2.1:

- `database.sql` still supplies the same v2 schema.
- first-run installer still generates the deployment RSA signing pair.
- private key is never displayed.
- installer/private-file protections remain in place.

Existing running deployment upgrade:

1. back up database/private/runtime files;
2. overwrite tracked application source with v5.2.1;
3. preserve `includes/config.local.php`, installation/encryption files and API v2 signing files;
4. if v2 is not ready, use **Admin -> Client Apps -> Initialize API v2** or the preserved CLI `php scripts/setup-v2.php` path;
5. existing valid signing keys are retained and verified.

The v5.2.1 delta requires no baseline file deletion, so Replace/Overwrite extraction is sufficient.
