# Licora v5.3.0 Updater Pre-Release Hotfix Audit

**Audited baseline:** GitHub `main` commit `67553727c44a2d5eecf51aef752151fb571a1a0f`  
**Release state:** v5.3.0 source is on `main`; no v5.3.0 tag/release has been published yet.  
**Hotfix version:** remains `5.3.0` because the release is still pre-tag/pre-publication.

## CI root cause

GitHub Actions ran `tests/api_v2_db_integration.php`, then `tests/admin_v2_ui_db_integration.php`, then `tests/updater_db_integration.php` against the same disposable MySQL database. The API v2 fixture intentionally creates only the tables it needs and does not create Licora's core `settings` table. The updater migration seeds updater settings after creating its three updater tables, so its final `INSERT INTO settings ...` failed with MySQL 1146.

This was a test-fixture isolation/prerequisite mismatch, not a MySQL 8.4 incompatibility and not an API v2 regression.

## Hotfix corrections

1. `tests/updater_db_integration.php` now owns its database prerequisites, first verifies the controlled missing-base-schema error, creates a production-compatible minimal `settings` table, then verifies schema initialization, setting seeds, coordinator lock, jobs/events/migration persistence, and corrupt-lock recovery.
2. `UpdateSchema` now validates the required core `settings(setting_key, setting_value)` contract and a single-column unique key before applying updater schema SQL. Missing/corrupt base schema returns `UPDATER_BASE_SCHEMA_MISSING` instead of a raw PDO engine failure.
3. Critical update lock metadata is atomically published. Corrupt/truncated lock JSON is recoverable both during ordinary request boot and updater bootstrap, preventing malformed metadata from indefinitely stranding normal traffic in 503.
4. Signed manifests now require an explicit non-empty `upgrade_from` source-version list. Runtime verification blocks unsupported direct jumps before any mutation, preventing silent migration-history skips.
5. Release spec/manifest builder validates stable channel and compatibility version formats, duplicate source/delete/package paths, and protocol-v1 control-file deletion.
6. Protocol v1 refuses deletion of updater control files (`includes/updater/*`, update AJAX controller, updater page/assets, `includes/config.php`) during a self-update.
7. Any release that carries migrations now acquires the critical application lock before the resumable/chunked database safety dump, avoiding internally inconsistent backups caused by concurrent normal Licora writes.
8. `updater_auto_check=0` now truly suppresses automatic outbound GitHub checks; explicit Super Admin manual checks remain available.

## Verified real features / no demo substitution

- Update Center state/jobs/events are database-backed.
- Live VibTools modal consumes `update_events`; no static deployment rows are used at runtime.
- Search, level filtering, Copy Logs, Download Diagnostics, pin-to-bottom, progress/stage, and resume are implemented.
- The Sandbox-only `AI Diagnostics` control is intentionally absent; no fake AI diagnostic backend is claimed.
- Release transport is pinned to the official GitHub repository/allowed GitHub HTTPS hosts.
- Manifest signature, package hash, per-file hashes, protected paths, archive root/traversal/symlink checks, staging, source backup, migration ledger, apply, post-verify, and source rollback are implemented.

## Known protocol-v1 limitations retained (not represented as completed features)

- Database backup is a retained safety SQL dump, not an automatic full-database restore engine. Signed migration rollback plus source rollback is automatic where defined; external production backup remains required.
- Updater runtime/jobs/backups/events are retained for diagnostics/manual rollback; automatic retention cleanup is not yet implemented.
- Update-signing key rotation has no dual-key transition protocol yet.
- The updater follows GitHub's latest stable release. Maintainers must publish latest releases with a compatible signed `upgrade_from` path and all migrations required by every supported direct jump.
- `updater_channel` is currently a reserved `stable` marker, not a selectable beta/dev channel.

## Verification boundary

Local source/static/manifest/state/UI verification passes. A local dedicated MySQL service and PHP `ZipArchive` are unavailable in the audit runtime, so the MySQL integration correction must be proven by the next GitHub Actions MySQL 8.4 run before tagging v5.3.0. The release tag must not be created while CI is red.
